# Code review sweep — watcher, predictive, summary, locks

Follow-up review beyond the Merkle snapshot engine
([snapshot-engine-review.md](snapshot-engine-review.md)): change watcher,
predictive hydration, catch-up summary, and process locks. All fixes shipped
in this session; evidence below.

## Fixed

- [x] **L1 — Live-process locks could be broken by the age cap.**
  `SyncLock`/`LandLock`/`DispatcherLock` staleness treated a lock as stale
  after 600 s even when the owning process was still alive, so a second sync
  could break a legitimate long-running sync (large chunked uploads over slow
  links exceed 10 minutes) and run concurrently; `is_sync_lock_active` could
  also misreport tray state. *Fix (`agent-core/src/lock.rs`): dead pid → stale
  immediately; live pid → stale only after a 24 h PID-reuse guard; same-pid
  re-acquire refreshes the lock timestamp.* Tests cover live-old, dead, and
  unparsable locks.
- [x] **P1 — Predictive hydration never cleared the placeholder readonly bit.**
  `hydrate_one` materialized without `set_readonly(false)`, so on Windows the
  atomic rename over the 0-byte placeholder fails and prefetch silently never
  hydrated anything (the error was swallowed). *Fix (`client/src/predictive.rs`):
  clear readonly first (matching `do_hydrate`), and log a warning instead of
  failing silently.*
- [x] **S1 — `--summarize` failed hard on a broken summary tool.**
  `FEANORFS_SUMMARY_CMD` that exits without reading stdin produced EPIPE and
  errored the whole command instead of falling back to the plain path listing.
  *Fix (`client/src/summary.rs`): broken pipe is tolerated (child reaped,
  empty output falls back to plain paths).*
- [x] **R1 — Chunked conflict legs could be dropped from reachability
  manifests.**
  `snapshot_reachability` expanded conflict legs' chunks using the *visible*
  leg's size (the tree format stores only that size), so a large hidden leg
  (e.g. an agent's chunked edit vs a small cloud version, carried into the tree
  by `agent land`/`undo`) never listed its chunks — server GC could then delete
  them and later `conflicts keep --cloud` materialization would fail with a
  missing blob. *Fix (`agent-core/src/objects.rs` + `large_file.rs`):
  `reachable_chunks` takes `Option<u64>`; hidden legs are size-unknown and
  inspect the blob itself, visible legs keep the fast path.* Two regression
  tests cover hidden-chunked and visible-chunked conflicts.
- [x] **F1 — C ABI dereferenced raw pointers without null guards.**
  18 of 20 `ffs_*` functions called `CStr::from_ptr` on required
  `*const c_char` arguments with no NULL check — undefined behavior (crash)
  for any caller passing NULL. *Fix (`feanorfs-ffi/src/lib.rs`): a
  `cstr_req` helper rejects NULL before dereferencing and is used for every
  required string argument, including the workspace root; optional strings
  already used the null-checked `cstr_opt`. Regression test passes NULL root
  and expects a clean NULL + thread-local error.* `feanorfs.h` regenerated by
  the build (integrator/agent-send declarations, previously missing).
- [x] **W1 — Watcher ignore for temp files was over-broad.**
  Any path component starting with `.feanorfs-tmp-` was ignored, so a real
  user file sharing the prefix never triggered a watcher sync. *Fix
  (`client/src/watch.rs`): only numeric-segment temp names
  (`.feanorfs-tmp-<pid>-<seq>-<attempt>`) are ignored; added tests.*

## Supervisor subsystem review

Reviewed `client/src/cli/supervisor.rs` (work-in-progress from a parallel
session; fixes applied once the tree settled).

- [x] **S1 — `stray_workspace_watcher` signaled arbitrary PIDs from
  `watch.pid`.** The reconcile loop read the workspace `watch.pid` file and, if
  the PID was alive, SIGTERMed then SIGKILLed it — with no marker freshness
  check and no process-identity verification, so a stale marker whose PID was
  reused by an unrelated process could kill an innocent process, and a user's
  own foreground `feanorfs sync` watcher in a terminal was silently killed on
  first reconcile. *Fix: require a marker mtime younger than 10 minutes (live
  watchers refresh every 45 s) AND verify the target's command line references
  the FeanorFS binary and this workspace (`ps -p <pid> -o command=`); non-Unix
  platforms conservatively report no strays (the sync lock still serializes).*
- [x] **S2 — supervisor single-instance guard was check-then-act.** The startup
  check read the published status file and bailed if another live supervisor
  pid existed, but nothing atomically claimed ownership; two supervisors
  started together could both proceed and race to spawn the hub/workers. *Fix:
  an `fs2` exclusive lock on `~/.feanorfs/supervisor.lock` (0600, never
  removed — ownership transfers safely on crash), taken at the top of
  `run_supervisor`.*

## Supervisor subsystem review — round 2 (restart policy, status, migration)

Follow-up review of `client/src/cli/supervisor.rs` (and its `service.rs`
integration) after the first fixes landed.

- [x] **S5 — `restart_on_zero_exit` was not honored by the respawn loop.**
  The desired-set diff spawned ANY missing child, so a child that exited
  cleanly (the user quitting the tray, a deliberate hub shutdown) was
  relaunched within one 500 ms poll, and a clean-exit child spun forever
  without engaging backoff. *Fix: extracted `should_respawn` — a child with
  `last_exit == Some(0)` and `restart_on_zero_exit == false` stays stopped;
  crash exits still restart with backoff. Regression tests cover fresh, clean,
  crash, explicit-restart, and backoff-held states.*
- [x] **S3 — status publication raced the 5 s wait timeouts.**
  The status file was published only on a 5-second heartbeat and never right
  after the first reconcile, so `service install|start|stop` (which wait at
  most 5 s against the status file) could time out even though the children
  were running. *Fix: `reconcile` reports whether anything changed and the
  loop publishes on change — including the very first pass — so Running/Stopped
  is observable within one poll.*
- [x] **S9 — idle status churn.** With publish-on-change in place the 5-second
  heartbeat write was dropped entirely (the status file is written only when
  state changes; supervisor liveness comes from `status.pid` + `pid_alive`).
- [x] **S11 — destructive legacy-job migration ran before the supervisor was
  proven running.** `ensure_supervisor_running` (and `refresh_installation`)
  uninstalled the legacy per-component launchd jobs and deleted their plists
  before the supervisor job had reached Running — a supervisor startup failure
  would leave the machine with no background services at all. *Fix: reorder —
  seed registry, install the supervisor job, wait for Running, and only then
  migrate legacy jobs (the supervisor's stray-watcher detection and the hub
  port bind handle the brief overlap).*

## Supervisor subsystem review — round 3 (cross-platform, resilience, migration)

- [x] **S12 — Windows would run two trays.** `desired_specs` added a tray
  child on every platform, while `install_tray_if_available` installs a
  separate Windows scheduled task (the code comment says only macOS/Linux run
  the tray inside the supervisor). On Windows the supervisor child and the
  task would race the tray's single-instance lock on every login. *Fix: gate
  the supervisor tray child to `#[cfg(not(target_os = "windows"))]`.*
- [x] **S13 — a transient registry problem killed the whole supervisor.** The
  loop propagated `read_registry()`/`desired_specs()`/`reconcile()` errors
  with `?`, so a corrupt `supervisor.json` or lock contention exited the
  supervisor — orphaning every child process until launchd restarted it (and
  a corrupt registry would crash-loop forever). *Fix: log and retry next poll,
  keeping the current children.*
- [x] **S14 — legacy migration read the wrong plist argument index.** Legacy
  workspace jobs run `feanorfs service run <workspace>` (workspace at
  ProgramArguments index 3); `legacy_jobs()` read index 2 (the literal
  `"run"` subcommand), resolving the marker against a junk path and creating a
  stray workspace-state directory during migration. *Fix: index 3, with a
  macOS plutil-based regression test.*

## Supervisor subsystem review — round 4 (restart lifecycle)

- [x] **S15 — orphaned children wedged the new supervisor after a restart.**
  When the supervisor is replaced (binary update, crash, or a shutdown that
  exceeded launchd's grace), its children are orphaned but keep running. The
  workspace watchers self-healed via stray detection and the tray via its
  instance lock, but the orphaned **hub** held the hub-data runtime lock and
  the listen port, so the new supervisor's hub child failed to bind and
  backoff-looped forever (`hub_status`/doctor reported Stopped while the
  orphan served traffic). *Fix: `reap_orphaned_children` at startup — before
  spawning anything, the supervisor reads the previous instance's status file
  and terminates any still-live recorded child pids (identity-verified against
  the command line, so a reused pid is never signaled).*
- [x] **S16 — stale status file after a cold start.** With publish-on-change,
  a supervisor that starts with an empty registry published nothing, leaving
  readers looking at the previous instance's status (old pid, old children).
  *Fix: publish an initial empty status immediately after startup (and after
  reaping orphans).*

## Supervisor subsystem review — round 6 (last-mile error paths)

- [x] **S17 — status-publish failures still killed the supervisor.** The two
  remaining `?` sites in the run loop were the initial and on-change
  `publish_status` calls; a failed status write (e.g. disk full) exited the
  supervisor, and launchd would restart it straight back into the same
  failure. *Fix: log and continue; a status write is never worth losing the
  supervision of every child.*
- [ ] **S18 — TLS leaf changes do not restart the supervised hub (minor,
  accepted).** `start --host` refreshes the TLS leaf in-process, but the
  supervisor only watches `relay.json`/`listen-port` mtimes, so the running
  hub keeps its old leaf until the next natural restart. Impact is low: the
  leaf's CA-bound mDNS hostname SAN is stable, so hostname-based clients
  validate fine across IP changes; only raw-IP clients could fail until the
  restart. Also noted: after the user quits the tray (S5 keeps it stopped),
  `refresh_installation` still reports the tray as Running because the
  supervisor job is up — cosmetic.

## Supervisor subsystem review — round 5 (integration verification + live ship)

Verified without code changes: `supervisor_job_state` (service_manager on
macOS/Linux, schtasks on Windows), `finish_sync_watch` Foreground/Background
semantics (stop-before-sync, lock-held initial sync, restore-on-failure), and
the `ensure_private_hub` provisioning order. The reviewed fixes were then
shipped to the live supervisor on this machine: rebuilt `target/release`,
`launchctl kickstart` the `com.feanorfs.agent` job, and confirmed all children
(hub, tray, 3 watchers) respawned running with zero restarts and `doctor` fully
green.

## Live deployment observations

The supervisor feature is now active on this machine (launchd `com.feanorfs.agent`,
KeepAlive-on-failure, running the repo's `target/release` build): three workspace
watchers, the private hub, and the tray are all supervised and report `running`
with zero restarts. The legacy per-component launchd jobs were migrated (deleted)
by this deployment, which is the migration path S11 now makes non-destructive
for future installs.

## Notes (not changed)

- Supervisor residuals accepted as minor: `migrate_legacy_jobs` swallows
  individual uninstall errors (a failed legacy uninstall leaves a duplicate
  watcher that the sync lock still serializes), and the stray-watcher identity
  check has a tiny check-to-signal window (mitigated by the freshness and
  command-line verification).
- Watch loop performs a full sync every 45 s even when idle (by design, to
  catch missed events); each sync is O(n) in the flat-view design — see
  snapshot-engine-review O6.
- `SyncLock` staleness semantics documented in `agent-core/AGENTS.md`; the fix
  aligns with the existing "native process-liveness checks" contract.
